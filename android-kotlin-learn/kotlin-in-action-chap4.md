# 4장. 클래스, 객체, 인터페이스

> 코틀린의 클래스와 인터페이스는 자바 클래스, 인터페이스와는 약간 다르다. 예를 들어 인터페이스에 프로퍼티 선언이 들어갈 수 있다. 자바와 달리 코틀린 선언은 기본적으로 `final` 이며 `public` 이다. 게다가 중첩 클래스는 기본적으로는 내부 클래스가 아니다. 즉, 코틀린 중첩 클래스에는 외부 클래스에 대한 참조가 없다.

> 짧은 주 생성자 구문으로도 거의 모든 경우를 잘 처리할 수 있다. 하지만 복잡한 초기화 로직을 수행하는 경우를 대비한 완전한 문법도 있다. 프로퍼티도 마찬가지다. 간결한 프로퍼티 구문으로도 충분히 제 몫을 하지만, 필요하면 접근자를 직접 정의할 수 있다.

> 코틀린 컴파일러는 번잡스러움을 피하기 위해 유용한 메소드를 자동으로 만들어준다. 클래스를 `data`로 선언하면 컴파일러가 일부 표준 메소드를 생성해준다. 그리고 코틀린 언어가 제공하는 위임을 사용하면 위임을 처리하기 위한 준비 메소드를 직접 작성할 필요가 없다.

> 4장에서는 클래스와 인스턴스를 동시에 선언하면서 만들 때 쓰는 `object` 키워드에 대해 설명한다. 싱글턴 클래스, 동반 객체(companion object), 객체 식(object expression - 자바의 anonymous class에 해당)을 표현할 때 `object` 키워드를 쓴다. 먼저 클래스와 인터페이스에 대해 이야기하고 코틀린에서 클래스 계층을 정의할 때 주의해야 할 점에 대해 살펴보자.

## 4.1 클래스 계층 정의

> 코틀린 가시성/접근 변경자는 자바와 비슷하지만 아무것도 지정하지 않은 경우 기본 가시성은 다르다. 또한 코틀린에서 새로 도입한 sealed 변경자에 대해 설명한다. sealed는 클래스 상속을 제한한다.

### 4.1.1 코틀린 인터페이스

> 코틀린 인터페이스는 자바 8 인터페이스와 비슷하다. 코틀린 인터페이스 안에는 추상 메소드뿐 아니라 구현이 있는 메소드도 정의할 수 있다(이는 자바 8 의 디폴트 메소드와 비슷하다). 다만 인터페이스에는 아무런 상태(필드)도 들어갈 수 없다.

> 코틀린에서 클래스는 `class`로 정의하지만 인터페이스는 interface를 사용한다.

리스트 4.1 간단한 인터페이스 선언하기

```kotlin
interface Clickable {
    fun click()
}
```

> 이 코드는 click이라는 추상 메소드가 있는 인터페이스를 정의한다. 이 인터페이스를 구현하는 모든 비추상 클래스(또는 구체적 클래스)는 click에 대한 구현을 제공해야 한다. 다음은 이 인터페이스를 구현하는 방법을 보여준다.

리스트 4.2 단순한 인터페이스 구현하기

```kotlin
class Button: Clickable {
    override fun click() = println("I was clicked")
}

Button().click()
// I was clicked
```

> 자바에서는 extends와 implements 키워드를 사용하지만, 코틀린에서는 클래스 이름 뒤에 콜론(:)을 붙이고 인터페이스와 클래스 이름을 적는 것으로 클래스 확장과 인터페이스 구현을 모두 처리한다. 자바와 마찬가지로 클래스는 인터페이스르 원하는 만큼 개수 제한 없이 마음대로 구현할 수 있지만, 클래스는 오직 하나만 확장할 수 있다.

> 자바의 @Override 애노테이션과 비슷한 override 변경자는 상위 클래스나 상위 인터페이스에 있는 프로퍼티나 메소드를 오버라이드한다는 표시다. 하지만 자바와 달리 코틀린에서는 override 변경자를 꼭 사용해야 한다. override 변경자는 실수로 상위 클래스의 메소드를 오버라이드 하는 경우를 방지해준다. 상위 클래스에 있는 메소드와 시그니처가 같은 메소드를 우연히 하위 클래스에서 선언하는 경우 컴파일이 안 되기 때문에 override를 붙이거나 메소드 이름을 바꿔야만 한다.

> 인터페이스 메소드도 디폴트 구현을 제공할 수 있다. 그런 경우 메소드 앞에 default를 붙여야 하는 자바 8과 달리 코틀린에서는 메소드를 특별한 키워드로 꾸밀 필요가 없다. 그냥 메소드 본문을 메소드 시그니처 뒤에 추가하면 된다. Clickable에 디폴트 구현이 포함된 메소드를 하나 추가해보자.

리스트 4.3 인터페이스 안에 본문이 있는 메소드 정의하기

```kotlin
interface Clickable {
    fun click() // 일반 메소드 선언
    fun showOff() = println("I'm clickable") // 디폴트 구현이 있는 메소드
}
```

> 이 인터페이스를 구현하는 클래스는 click에 대한 구현을 제공해야 한다. 반면 showOff 메소드의 경우 새로운 동작을 정의할 수도 있고, 그냥 정의를 생략해서 디폴트 구현을 사용할 수도 있다.

> 이제 showOff 메소드를 정의하는 다른 인터페이스가 다음과 같은 구현을 포함한다고 하자.

리스트 4.4 동일한 메소드를 구현하는 다른 인터페이스 정의

```kotlin
interface Focusable {
    fun setFocus(b: Boolean) =
        println("I ${if (b) "got" else "lost"} focus.")
    fun showOff() = println("I'm focusable!")
}
```

> 한 클래스에서 이 두 인터페이스를 함께 구현하면 어떻게 될까? 두 인터페이스 모두 디폴트 구현이 들어있는 showOff 메소드가 있다. 어느 쪽 showOff 메소드가 선택될까? 어느 쪽도 선택되지 않는다. 클래스가 구현하는 두 상위 인터페이스에 정의된 showOff 구현을 대체할 오버라이딩 메소드를 직접 제공하지 않으면 다음과 같은 컴파일 오류가 발생한다.

```kotlin
The class 'Button' must
override public open fun showOff() because it inherits
many implementations of it.
```

코틀린 컴파일러는 두 메소드를 아우르는 구현을 하위 클래스에 직접 구현하게 강제한다.

리스트 4.5 상속한 인터페이스의 메소드 구현 호출하기

```kotlin
class Button : Clickable, Focusable {
    override fun click() = println("I was clicked")
    // 이름과 시그니처가 같은 멤버 메소드에 대해 둘 이상의 디폴트 구현이 있는 경우 인터페이스를 구현하는 하위 클래스에서 명시적으로 새로운 구현을 제공해야 한다.
    override fun showOff() {
        // 상위 타입의 이름을 꺽쇠 괄호(<>) 사이에 넣어서 "super"를 지정하면
        // 어떤 상위 타입의 멤버 메소드를 호출할지 지정할 수 있다.
        super<Clickable>.showOff()
        super<Focusable>.showOff()
    }
}
```

> Button 클래스는 이제 이 두 인터페이스를 구현한다. Button은 상속한 두 상위 타입의 showOff() 메소드를 호출하는 방식으로 showOff()를 구현한다. 상위 타입의 구현을 호출할 때는 자바와 마찬가지로 super를 사용한다. 하지만 구체적으로 타입을 지정하는 문법은 다르다. 자바에서는 Clickable.super.showOff() 처럼 super 앞에 기반 타입을 적지만, 코틀린에서는 super<Clickable>.showOff() 처럼 꺽쇠 괄호 안에 기반 타입 이름을 지정한다.

> 상속한 구현 중 단 하나만 호출해도 된다면 다음과 같이 쓸 수도 있다.

`override fun showOff() = super<Clickable>.showOff()`

### 4.1.2 open, final, abstract 변경자: 기본적으로 final

> 여러분이 아는 대로 자바에서는 final로 명시적으로 상속을 금지하지 않는 모든 클래스를 다른 클래스가 상속할 수 있다. 이렇게 기본적으로 상속이 가능하면 편리한 경우도 많지만 문제가 생기는 경우도 많다.

> 취약한 기반 클래스(fragile base class)라는 문제는 하위 클래스가 기반 클래스에 대해 가졌던 가정이 기반 클래스를 변경함으로써 깨져버린 경우에 생긴다. 어떤 클래스가 자신을 상속하는 방법에 대해 정확한 규칙(어떤 메소드를 어떻게 오버라이드해야 하는지 등)을 제공하지 않는다면 그 클래스의 클라이언트는 기반 클래스를 작성한 사람의 의도와 다른 방식으로 메소드를 오버라이드할 위험이 있다. 모든 하위 클래스를 분석하는 것은 불가능하므로 기반 클래스를 변경하는 경우 하위 클래스의 동작이 예기치 않게 바뀔 수도 있다는 면에서 기반 클래스는 '취약'하다.

> 이 문제를 해결하기 위해 자바 프로그래밍 기법에 대한 책 중 가장 유명한 책인 조슈아 블로크(Joshua Block)가 쓴 "Effective Java"에서는 "상속을 위한 설계와 문서를 갖추거나, 그럴 수 없다면 상속을 금지하라"라는 조언을 한다. 이는 특별히 하위 클래스에서 오버라이드하게 의도된 클래스와 메소드가 아니라면 모두 final로 만들라는 뜻이다.

> 코틀린도 마찬가지 철학을 따른다. 자바의 클래스와 메소드는 기본적으로 상속에 대해 열려있지만 코틀린의 클래스와 메소드는 기본적으로 final이다.

> 어떤 클래스의 상속을 허용하려면 클래스 앞에 open 변경자를 붙여야 한다. 그와 더불어 오버라이드를 허용하고 싶은 메소드나 프로퍼티의 앞에도 open 변경자를 붙여야 한다.

리스트 4.6 열린 메소드를 포함하는 열린 클래스 정의하기

```kotlin
open class RichButton: Clickable {
    fun disable() {} // 이 함수는 final이다. 하위 클래스가 이 메소드를 오버라이드할 수 없다.
    open fun animate() {} // 이 함수는 열려있고, 하위 클래스에서 이 메소드를 오버라이드해도 된다.
    override fun click() {} // 이 함수는 (상위 클래스에서 선언된) 열려 있는 메소드를 오버라이드한다. 오버라이드한 메소드는 기본적으로 열려있다.
}
```

> 오버라이드하는 메소드의 구현을 하위 클래스에서 오버라이드하지 못하게 금지하려면 오버라이드하는 메소드 앞에 `final`을 명시해야 한다.

```kotlin
open class RichButton: Clickable {
    final override fun click() {}
    // 위의 final은 쓸데 없이 붙은 중복이 아니다. final이 없는 override 메소드나 프로퍼티는 기본적으로 열려있다.
}
```

#### 열린 클래스와 스마트 캐스트

> 클래스의 기본적인 상속 가능 상태를 `final`로 함으로써 얻을 수 있는 큰 이익은 다양한 경우에 스마트 캐스트가 가능하다는 점이다. 2.3.5 절에서 말한 것처럼 스마트 캐스트는 타입 검사 뒤에 변경될 수 없는 변수에만 적용 가능하다. 클래스 프로퍼티의 경우 이는 `val`이면서 커스텀 접근자가 없는 경우에만 스마트 캐스트를 쓸 수 있다는 의미다. 이 요구 사항은 또한 프로퍼티가 `final`이어야만 한다는 뜻이기도 하다. 프로퍼티가 `final`이 아니라면 그 프로퍼티를 다른 클래스가 상속하면서 커스텀 접근자를 정의함으로써 스마트 캐스트의 요구 사항을 깰 수 있다. 프로퍼티는 기본적으로 `final`이기 때문에 따로 고민할 필요 없이 대부분의 프로퍼티를 스마트 캐스트에 활용할 수 있다. 이는 코드를 더 이해하기 쉽게 만든다.

---

#### 1. 프로퍼티가 기본적으로 `final`이라는 것이 `val`을 의미하는가?

**아닙니다. `val`과 `final`은 서로 다른 개념입니다.** 하지만 코틀린에서는 이 두 개념이 긴밀하게 결합되어 동작합니다.

- **`val` (읽기 전용):** 재할당이 불가능한 변수나 프로퍼티를 의미합니다. (자바의 `final String name`과 유사)
- **`final` (상속/오버라이드 금지):** 하위 클래스에서 이 프로퍼티를 **재정의(Override)할 수 없음**을 의미합니다.

코틀린에서 프로퍼티를 선언할 때, 기본적으로 다음 두 가지 특징을 가집니다.

1. `val`로 선언하면 읽기 전용 프로퍼티가 됩니다.
2. 동시에, 명시적으로 `open`을 붙이지 않는 한 **기본적으로 `final` 상태**가 됩니다. 즉, 하위 클래스에서 이 프로퍼티를 오버라이드하여 커스텀 게터(getter)를 작성하는 등의 재정의를 할 수 없습니다.

### 2. 열린 클래스(open)와 스마트 캐스트(Smart Cast)의 관계 보충 설명

스마트 캐스트가 작동하려면 **"타입을 검사한 시점의 값과 실제로 사용하는 시점의 값이 완전히 동일하다"** 는 보장이 있어야 합니다. 값이 중간에 바뀔 가능성이 조금이라도 있다면 컴파일러는 스마트 캐스트를 허용하지 않습니다.

만약 프로퍼티가 `final`이 아니라 **`open` (열려 있음)** 상태라면 어떤 문제가 생기는지 예시를 통해 보겠습니다.

#### 만약 프로퍼티가 `open` 일 때 발생하는 문제 (스마트 캐스트 불가능)

```kotlin
// 열려 있는 부모 클래스
open class User {
    // open 프로퍼티: 하위 클래스에서 오버라이드할 수 있음
    open val name: String? = "John"
}

// User를 상속받은 자식 클래스
class VolatileUser : User() {
    // 부모의 name을 오버라이드하여 호출할 때마다 값이 바뀌는 커스텀 게터를 만듦
    override val name: String?
        get() = if (Math.random() > 0.5) "Alice" else null
}
```

이 상황에서 아래와 같은 스마트 캐스트 코드를 작성했다고 가정해 보겠습니다.

```kotlin
fun printLength(user: User) {
    if (user.name != null) {
        // null 검사를 통과함!
        // 하지만 user가 VolatileUser 인스턴스라면?
        // 바로 아래 줄에서 user.name을 호출할 때 다시 커스텀 게터가 실행되어 null이 반환될 수도 있습니다.
        println(user.name.length) // 에러 발생 가능성 존재 -> 스마트 캐스트 불가능
    }
}
```

컴파일러 입장에서는 `user`가 `User`를 상속받은 `VolatileUser`일 수도 있기 때문에, `user.name`이 항상 `null`이 아니라고 확신할 수 없습니다. 따라서 스마트 캐스트를 해주고 싶어도 해줄 수 없습니다.

#### 프로퍼티가 기본값인 `final` 일 때 (스마트 캐스트 가능)

반면 코틀린의 기본 설정대로 프로퍼티가 `final`이면 하위 클래스에서 이 프로퍼티를 오버라이드하여 임의로 값을 바꾸는 커스텀 게터를 지정할 수 없습니다.

```kotlin
open class User {
    // 기본적으로 final 프로퍼티 (open이 없으므로 자식 클래스에서 재정의 불가)
    val name: String? = "John"
}
```

이 경우 컴파일러는 `user.name`이 오버라이드되어 값이 예측 불가능하게 바뀔 리 없다는 것을 안전하게 확신할 수 있습니다. 따라서 아래 코드에서 **스마트 캐스트가 정상 작동**합니다.

```kotlin
fun printLength(user: User) {
    if (user.name != null) {
        // 컴파일러가 안심하고 String? 타입을 String 타입으로 스마트 캐스트해 줍니다.
        println(user.name.length)
    }
}
```

#### 요약하자면

코틀린은 클래스와 프로퍼티를 기본적으로 `final`로 강제함으로써, **"자식 클래스에서 꼼수로 값을 바꾸는 일"** 을 원천 차단합니다. 그 덕분에 컴파일러가 안심하고 스마트 캐스트를 적극적으로 적용해 줄 수 있어 개발자가 더 편리하게 코딩할 수 있게 됩니다.

---

> 자바처럼 코틀린에서도 클래스를 abstract로 선언할 수 있다. abstract로 선언한 추상 클래스는 인스턴스화할 수 없다. 추상 클래스에는 구현이 없는 추상 멤버가 있어서 하위 클래스에서 그 추상 멤버를 오버라이드해야만 하는 게 보통이다. 추상 멤버는 항상 열려있다. 따라서 추상 멤버 앞에 open 변경자를 명시할 필요가 없다.

리스트 4.8 추상 클래스 정의하기

```kotlin
abstract class Animated { // 이 클래스는 추상 클래스다. 이 클래스의 인스턴스를 만들 수 없다.
    abstract fun animate() // 이 함수는 추상 함수다. 이 함수에는 구현이 없다. 하위 클래스에서는 이 함수를 반드시 오버라이드해야 한다.
    open fun stopAnimating() {} // 추상 클래스에 속했더라도 비추상 함수는 기본적으로 final이지만 원한다면 open으로 오버라이드를 허용할 수 있다.
    fun animateTwice() {

    }

}

```

표 4.1 클래스 내에서 상속 제어 변경자의 의미

| 변경자   | 이 변경자가 붙은 멤버는...                              | 설명                                                                                                      |
| -------- | ------------------------------------------------------- | --------------------------------------------------------------------------------------------------------- |
| final    | 오버라이드할 수 없음                                    | 클래스 멤버의 기본 변경자다.                                                                              |
| open     | 오버라이드할 수 있음                                    | 반드시 open을 명시해야 오버라이드할 수 있다.                                                              |
| abstract | 반드시 오버라이드해야 함                                | 추상 클래스의 멤버에만 이 변경자를 붙일 수 있다. 추상 멤버에는 구현이 있으면 안된다.                      |
| override | 상위 클래스나 상위 인스턴스의 멤버를 오버라이드 하는 중 | 오버라이드하는 멤버는 기볹거으로 열려있다. 하위 클래스의 오버라이드를 금지하려면 final을 명시해야만 한다. |

### 4.1.3 가시성 변경자: 기본적으로 공개

> 가시성 변경자visibility modifier는 코드 기반에 있는 선언에 대한 클래스 외부 접근을 제어한다. 어떤 클래스의 구현에 대한 접근을 제한함으로써 그 클래스에 의존하는 외부 코드를 깨지 않고도 클래스 내부 구현을 변경할 수 있다.

> 기본적으로 코틀린 가시성 변경자는 자바와 비슷하다. 자바와 같은 public, protected, private 변경자가 있다. 하지만 코틀린의 기본 가시성은 자바와 다르다. 아무 변경자도 없는 경우 선언은 모두 공개(public)된다.

> 자바의 기본 가시성인 패키지 전용(package-private)은 코틀린에 없다. 코틀린은 패키지를 네임스페이스를 관리하기 위한 용도로만 사용한다. 그래서 패키지를 가시성 제어에 사용하지 않는다.

> 패키지 전용 가시성에 대한 대안으로 코틀린에는 internal이란느 새로운 가시성 변경자를 도입했다. internal은 "모듈 내부에서만 볼 수 있음"이라는 뜻이다. 모듈(module)은 한 번에 한꺼번에 컴파일되는 코틀린 파일들을 의미한다. 인텔리J나 이클립스, 메이븐, 그레이들 등의 프로젝트가 모듈이 될 수 있고, 앤트 테스크가 한 번 실행될 때 함께 컴파일되는 파일의 집합도 모듈이 될 수 있다.

> 모듈 내부 가시성은 여러분의 모듈의 구현에 대해 진정한 캡슐화를 제공한다는 장점이 있다. 자바에서는 패키지가 같은 클래스를 선언하기만 하면 어떤 프로젝트의 외부에 있는 코드라도 패키지 내부에 있는 패키지 전용 선언에 쉽게 접근할 수 있다. 그래서 모듈의 캡슐화가 쉽게 깨진다.

> 다른 차이는 코틀린에서는 최상위 선언에 대해 private 가시성(비공개 가시성)을 허용한다는 점이다. 그런 최상위 선언에는 클래스, 함수, 프로퍼티 등이 포함된다. 비공개 가시성인 최상위 선언은 그 선언이 들어있는 파일 내부에서만 사용할 수 있다. 이 또한 하위 시스템의 자세한 구현 사항을 외부에 감추고 싶을 때 유용한 방법이다.

---

#### 코틀린 vs 자바의 가시성 변경자(Visibility Modifier)

#### 1. 아무것도 붙이지 않았을 때의 기본 가시성 (Default)

가장 먼저 와닿는 차이는 접근 제어자를 생략했을 때 적용되는 기본값입니다.

| 구분            | 자바 (Java)                       | 코틀린 (Kotlin)    |
| :-------------- | :-------------------------------- | :----------------- |
| **기본 가시성** | **패키지 전용 (package-private)** | **공개 (public)**  |
| **특징**        | 같은 패키지 내부에서만 접근 가능  | 어디서든 접근 가능 |

- **자바:** 아무것도 안 쓰면 같은 패키지 내의 클래스끼리만 볼 수 있습니다.
- **코틀린:** 아무것도 안 쓰면 `public`이 되어 프로젝트 어디서나 접근할 수 있습니다. 코틀린 개발진은 실제로 많은 클래스와 메서드가 `public`으로 선언된다는 점에 착안하여 기본값을 `public`으로 설정했습니다.

---

#### 2. 패키지 전용(Java) vs 모듈 전용(Kotlin `internal`)

자바의 '패키지 전용(package-private)' 가시성은 한계가 있습니다. 코틀린은 이를 보완하기 위해 `internal`이라는 가시성을 도입했습니다.

#### 자바의 패키지 전용 가시성의 문제점:

자바에서는 패키지 이름이 같으면 다른 라이브러리나 모듈에 있더라도 패키지 전용 멤버에 접근할 수 있습니다.

- 예를 들어, 내가 만든 외부 라이브러리에 `com.service`라는 패키지가 있고 그 안에 패키지 전용(default) 클래스가 있다고 가정해 보겠습니다.
- 라이브러리를 가져다 쓰는 사용자가 자신의 프로젝트에 똑같이 `com.service`라는 패키지를 만들고 클래스를 선언하면, 내 라이브러리의 패키지 전용 클래스에 직접 접근해 버릴 수 있습니다. 이로 인해 캡슐화가 쉽게 깨집니다.

---

#### [상황 설정]

여러분은 전 세계 개발자들이 쓸 수 있는 **'로그인 라이브러리(프로젝트)'** 를 개발하고 있습니다.

이 라이브러리 안에는 외부 사람들은 절대 직접 만지면 안 되고, 오직 내가 만든 코드끼리만 내부적으로 공유해야 하는 비밀번호 암호화 클래스(`CryptoHelper`)가 있습니다.

패키지 이름은 `com.login`으로 지정했습니다.

---

#### 1. 자바(Java)의 경우: "패키지 이름만 똑같이 만들면 뚫린다"

자바에서는 외부 노출을 막기 위해 `CryptoHelper` 클래스에 아무런 제어자도 붙이지 않는 **패키지 전용(Default)** 상태로 만듭니다.

```java
// [내가 만든 라이브러리 코드]
package com.login;

class CryptoHelper {  // 아무것도 안 붙임 (패키지 전용)
    void encrypt() { ... }
}
```

이제 이 라이브러리를 완성해서 `.jar` 파일로 배포했습니다.

그런데 내 라이브러리를 다운로드받아 쓰는 어떤 해커 개발자(사용자)가 이 비밀 암호화 클래스(`CryptoHelper`)를 강제로 꺼내서 쓰고 싶어졌습니다. 자바에서는 어떻게 편법을 쓸 수 있을까요?

1. 해커는 자기 프로젝트 안에 **똑같이 `com.login`이라는 이름의 패키지(폴더)** 를 만듭니다.
2. 그리고 그 폴더 안에 아래와 같이 코드를 작성합니다.

```java
// [해커의 프로젝트 코드]
package com.login; // 내 라이브러리와 똑같은 패키지 이름을 씀!

public class HackerCode {
    void hack() {
        // 에러 없이 실행됨!
        CryptoHelper helper = new CryptoHelper();
        helper.encrypt();
    }
}
```

- **자바가 허용하는 이유:** 자바 컴파일러는 물리적으로 다른 프로젝트(라이브러리)인지 상관하지 않고, 오직 **코드 맨 위에 적힌 패키지 이름(`package com.login;`)이 같은가?** 만 확인합니다. 같기 때문에 "아, 둘이 같은 패키지 식구구나" 하고 접근을 허용해 버립니다.
- **결과:** 내가 숨겨놓은 비밀 클래스의 캡슐화가 쉽게 깨져버립니다.

---

#### 2. 코틀린(Kotlin)의 경우: "프로젝트 경계(모듈)가 다르면 절대 안 된다"

코틀린에서는 이런 우회 접근을 막기 위해 **`internal`** 가시성을 사용합니다.

```kotlin
// [내가 만든 코틀린 라이브러리 코드]
package com.login

internal class CryptoHelper {  // internal 적용
    fun encrypt() { ... }
}
```

이 라이브러리를 배포한 후, 똑같은 해커가 자기 프로젝트에 `com.login` 패키지를 만들고 접근을 시도해 봅니다.

```kotlin
// [해커의 코틀린 프로젝트 코드]
package com.login // 패키지 이름을 똑같이 흉내 냄

class HackerCode {
    fun hack() {
        // 컴파일 에러 발생!
        // "CryptoHelper는 이 모듈 안에서만 쓸 수 있습니다(internal)"
        val helper = CryptoHelper()
    }
}
```

- **코틀린이 막아주는 이유:** 코틀린 컴파일러는 단순히 패키지 이름만 보지 않습니다. 이 코드가 **실제 동일한 프로젝트(동일한 빌드/컴파일 단위인 '모듈') 안에서 만들어진 코드인가?** 를 확인합니다.
- 라이브러리 프로젝트와 해커의 프로젝트는 엄연히 물리적으로 분리된 별개의 프로젝트(모듈)이므로, 패키지 이름을 아무리 똑같이 흉내 내도 코틀린 컴파일러는 접근을 철저히 차단합니다.

---

#### 3. 일상생활로 비유하자면

- **자바의 패키지 전용(Default):** "서울시 마포구 아파트 301호"라는 주소만 보고 열쇠를 열어주는 방식입니다. 내가 사는 곳이 아닌 다른 동네(다른 프로젝트)라도 똑같이 "마포구 아파트 301호"라는 명패만 달고 있으면 문을 열어주는 허점이 있습니다.
- **코틀린의 `internal`:** 주소뿐만 아니라 **"동일한 아파트 단지(모듈) 출입 카드"** 가 있는지 확인하는 방식입니다. 외부인이 자기 집 주소를 아무리 똑같이 위장하더라도, 우리 아파트 단지 카드가 없으면 단지 안으로 들어올 수 없습니다.

---

#### 코틀린의 해결책 (`internal`):

코틀린은 패키지 기준이 아닌, **컴파일 단위인 '모듈(Module)'** 을 기준으로 삼는 `internal`을 도입했습니다.

- **모듈이란?** 한 번에 같이 컴파일되는 단위(예: 하나의 Gradle 서브프로젝트, Maven 프로젝트, IntelliJ 모듈 등)를 말합니다.
- 개발자가 물리적으로 구분해 놓은 모듈 경계를 넘어서는 `internal` 선언에 절대 접근할 수 없습니다. 따라서 패키지 이름을 흉내 내어 우회 접근하는 것이 불가능하므로 훨씬 안전한 캡슐화가 가능합니다.

---

모듈이란 **"한 번에 빌드(컴파일)되는 하나의 묶음"** 이라는 표현이 기술적으로 가장 정확합니다.

---

#### 1. 왜 "하나의 프로젝트"보다 "빌드되는 하나의 묶음"이 더 정확한가요?

요즘 규모가 있는 개발 환경에서는 하나의 큰 '프로젝트'를 여러 개의 작은 단위로 쪼개서 개발하는 **멀티 프로젝트(멀티 모듈)** 방식을 자주 사용합니다.

예를 들어, 하나의 큰 쇼핑몰 시스템(전체 프로젝트)을 개발할 때 다음과 같이 쪼갤 수 있습니다.

- **쇼핑몰 프로젝트 (전체 프로젝트)**
  - 📦 **Core 모듈** (공통 비즈니스 로직, 데이터베이스 설정 등) -> `core.jar`로 빌드됨
  - 📦 **API 모듈** (사용자용 앱/웹 서버) -> `api.jar`로 빌드됨
  - 📦 **Admin 모듈** (관리자용 웹 서버) -> `admin.jar`로 빌드됨

이때 `Core`, `API`, `Admin` 각각이 바로 **하나의 모듈(빌드 묶음)** 입니다. 각각 독립적으로 컴파일되어 개별 결과물(`.jar` 파일 등)로 나오기 때문입니다.

---

#### 2. 이 구조에서 `internal`이 작동하는 방식

만약 **Core 모듈** 안에 `internal class CardPayment`라는 결제 관련 클래스를 만들었다고 가정해 보겠습니다.

- 이 클래스는 **Core 모듈** 안에서 빌드되는 코드끼리는 자유롭게 가져다 쓸 수 있습니다.
- 하지만 같은 전체 프로젝트 소속이더라도, 별도로 빌드되는 **API 모듈**이나 **Admin 모듈**의 코드에서는 이 `internal` 클래스에 접근할 수 없습니다. 컴파일러가 "서로 다른 빌드 묶음(모듈)"으로 인식하기 때문입니다.

---

#### 요약

- **"빌드되어 하나의 결과물(`.jar`, `.aar`, `.war` 등)로 출력되는 코드의 묶음"** 이 코틀린이 정의하는 가장 정확한 모듈의 단위입니다.
- 따라서 개발자가 인위적으로 분리해 놓은 빌드 묶음 경계를 넘어서지 못하게 막아주는 것이 `internal` 가시성입니다.

---

#### 3. 파일 최상위(Top-level)에서의 `private` 허용

자바와 달리 코틀린은 클래스 밖(파일의 최상위 레벨)에 함수나 변수를 직접 선언할 수 있습니다. 그리고 여기에 `private`을 붙일 수 있습니다.

```kotlin
// MyUtils.kt 파일 내부

private val debugMode = true // 이 파일 내부에서만 사용 가능

private fun logDebug(message: String) { // 이 파일 내부에서만 사용 가능
    if (debugMode) println(message)
}

class Utility {
    fun doSomething() {
        logDebug("작업 시작") // 같은 파일이므로 호출 가능
    }
}
```

- **자바:** 자바는 모든 코드가 클래스 내부에 있어야 하므로 파일 최상위에 `private` 변수나 함수를 단독으로 선언할 수 없습니다.
- **코틀린:** 파일 최상위에 `private`을 선언하면, **"오직 해당 파일(.kt) 내부에서만 사용할 수 있는 기능"** 이 됩니다. 다른 파일에 구현 내용을 숨겨야 할 때 매우 유용합니다.

---

#### 4. `protected` 변경자의 동작 방식 차이

상속 관계에서 쓰이는 `protected`도 자바와 코틀린에서 동작이 다릅니다.

- **자바의 `protected`:** 자신을 상속한 자식 클래스 **또는** 같은 패키지에 속한 다른 클래스라면 접근할 수 있습니다.
- **코틀린의 `protected`:** 오직 자신을 상속한 **자식 클래스 내부에서만** 접근할 수 있습니다. (같은 패키지에 있다고 해서 접근할 수 없습니다.)

코틀린은 패키지를 단순히 이름 공간(Namespace)을 나누는 용도로만 사용하기 때문에, 자바처럼 "같은 패키지라고 해서 접근을 허용"하는 예외를 두지 않고 오직 상속 관계에서만 통하도록 엄격하게 제어합니다.

---

> 예제를 하나 살펴보자. giveSpeech 함수 안의 각 줄은 가시성 규칙을 위반한다. 컴파일하면 오류를 볼 수 있다.

```kotlin
internal open class TalkativeButton: Focusable {
    private fun yell() = println("Hey!")
    protected fun whisper() = println("Let's talk!")
}

fun TalkativeButton.giveSpeech() {
// 오류: "public" 멤버가 자신의 "internal" 수신 타입인 "TalkativeButton"을 노출함
    yell()
    whisper() // 오류: "whisper"에 접근할 수 없음: "whisper"는 "TalkativeButton"의 "protected" 멤버임.
}
```

> 코틀린은 `public` 함수인 `giveSpeech` 안에서 그보다 가시성이 더 낮은 타입인 `TalkativeButton`을 참조하지 못하게 한다. 이는 어떤 클래스의 기반 타입 목록에 들어있는 타입이나 제네릭 클래스의 타입 파라미터에 들어있는 타입의 가시성은 그 클래스 자신의 가시성과 같거나 더 높아야 하고, 메소드의 시그니처에 사용된 모든 타입의 가시성은 그 메소드의 가시성과 같거나 더 높아야 한다는 더 일반적인 규칙에 해당한다. 이런 규칙은 어떤 함수를 호출하거나 어떤 클래스를 확장할 때 필요한 모든 타입에 접근할 수 있게 보장해준다. 여기서 컴파일 오류를 없애려면 `giveSpeech` 확장 함수의 가시성을 `internal`로 바꾸거나, `TalkativeButton` 클래스의 가시성을 `public`으로 바꿔야 한다.

---

#### 에러 1: "나(공개)는 보이지도 않는 너(비공개)를 소개할 수 없다" (공개범위 모순)

```kotlin
// 1. 이 클래스는 internal(우리 회사 사람만 볼 수 있음)입니다.
internal open class TalkativeButton : Focusable { ... }

// 2. 이 함수는 아무것도 안 붙었으니 public(전 세계 누구나 볼 수 있음)입니다.
fun TalkativeButton.giveSpeech() { ... } // <- 여기서 에러!
```

- **상황 비유:**
  - `TalkativeButton`은 우리 회사 내부에서만 쓰이는 기밀 문서(internal)입니다.
  - 그런데 `giveSpeech`라는 함수는 전 세계 누구나 볼 수 있는 홍보 책자(public)입니다.
  - 홍보 책자(public)에 기밀 문서(internal)의 이름과 사용법을 대대적으로 적어 놓은 꼴입니다. 외부 사람이 이 홍보 책자를 읽고 "나도 이거 써볼래!" 하고 기밀 문서를 찾으려고 하면, 정작 기밀 문서 자체는 볼 권한이 없어서 혼란이 생깁니다.
- **코틀린의 규칙:**
  - 전 세계에 공개된 `public` 함수는, 자신보다 공개 범위가 좁은 `internal` 클래스를 다루는 함수로 선언될 수 없습니다.
  - **해결법:** 외부인이 혼란스럽지 않게 홍보 책자(함수)도 우리 회사 사람만 볼 수 있도록 `internal fun TalkativeButton.giveSpeech()`로 격하시키거나, 기밀 문서(클래스)를 `public`으로 완전히 공개해야 합니다.

---

#### 에러 2: "외부인은 안방 비밀번호를 알 수 없다" (권한 부족)

```kotlin
internal open class TalkativeButton : Focusable {
    private fun yell() = println("Hey!") // 오직 이 클래스 내부에서만 호출 가능
    protected fun whisper() = println("Let's talk!") // 오직 자식 클래스 안에서만 호출 가능
}

fun TalkativeButton.giveSpeech() {
    yell()     // <- 에러! (접근 불가)
    whisper()  // <- 에러! (접근 불가)
}
```

- **상황 비유:**
  - 확장 함수(`giveSpeech`)는 클래스 **바깥**에서 정의된 함수입니다. 쉽게 말해 클래스의 '이웃 사촌'일 뿐입니다.
  - `yell()`은 집주인만 쓸 수 있는 안방 금고(`private`)이고, `whisper()`는 자식들에게만 물려주는 가업(`protected`)입니다.
  - 아무리 이웃 사촌(`giveSpeech`)이 친절하게 도와주려고 해도, 남의 집 안방 금고를 열거나 가업을 마음대로 쓸 권한은 없습니다.
- **코틀린의 규칙:**
  - 확장 함수는 클래스 외부에서 동작하는 함수이기 때문에, 그 클래스의 `private`이나 `protected` 멤버에는 절대 접근할 수 없습니다. 오직 공개된(`public` 또는 `internal`) 멤버만 사용할 수 있습니다.

---

#### 정리하자면

이 코드가 정상적으로 컴파일되려면 아래와 같이 고쳐야 합니다.

```kotlin
internal open class TalkativeButton : Focusable {
    // 1. 외부(확장 함수)에서도 쓸 수 있게 공개 범위를 public(또는 internal)으로 넓힙니다.
    fun yell() = println("Hey!")
    fun whisper() = println("Let's talk!")
}

// 2. 함수 앞에도 internal을 붙여서 클래스의 공개 범위(internal)와 맞춰줍니다.
internal fun TalkativeButton.giveSpeech() {
    yell()     // 이제 접근 가능
    whisper()  // 이제 접근 가능
}
```

> 자바에서는 같은 패키지 안에서 `protected` 멤버에 접근할 수 있지만, 코틀린에서는 그렇지 않다는 점에서 자바와 코틀린의 `protected`가 다르다는 사실에 유의하라. 코틀린의 가시성 규칙은 단순하다. `protected` 멤버는 오직 어떤 클래스나 그 클래스를 상속한 클래스 안에서만 보인다. 클래스를 확장한 함수는 그 클래스의 `private`이나 `protected` 멤버에 접근할 수 없다는 사실을 기억하자.
