## YUV_420_888이란?
정식 명칭은 `android.graphics.ImageFormat.YUV_420_888`은 안드로이드 Camera2 API 및 미디어 프레임워크에서 카메라 센서/ISP가 처리한 비압축(Raw) 프레임을 전달하기 위해 사용하는 범용 표준 포맷

이름을 분해하면 [YUV 색 공간] + [4:2:0 크로마 서브샘플링] + [채널당 8비트(888)]의 조합

### 1.YUV 색 공간(Color Space)
흔히 쓰는 RGB는 빛의 삼원색(Red, Green, Blue)을 각각 저장하지만, YUV는 사람의 눈(시각 인지 체계) 특성에 맞춰 정보를 분리함
- Y(Luma, 휘도): 영상의 밝기(명암, 흑백) 정보. 인간의 눈은 색상 변화보다 밝기 변화와 윤곽선에 훨씬 민감함
- U(Cb, Chrominance Blue): 밝기에서 파란색 성분을 뺀 색차 정보
- V(Cr, Chrominance Red): 밝기에서 빨간색 성분을 뺀 색차 정보

### 2. 4:2:0 크로마 서브샘플링 (Chroma Subsampling)
사람의 눈이 색상 해상도에는 둔감하다는 점을 이용해 데이터 크기를 줄이는 방식
```
[4개 픽셀 기준 (2x2 블록)]
Y0  Y1        
Y2  Y3   +   U (1개)   +   V (1개)
```
- Y 성분: 모든 픽셀마다 1:1로 온전하게 캡처함 (해상도 $W X H$)
- U, V 성분: 가로와 세로 모두 2픽셀 마다 1개씩 샘플링함 (해상도 각 $\frac{W}{2} X \frac{H}{2}$, 면적 기준 1/4)
- 데이터 크기 비교:
    - RGB888: 픽셀당 3바이트 (24bpp, Bits Per Pixel)
    - YUV420: 픽셀당 1바이트(Y) + 0.25바이트(U) + 0.25바이트(V) = 1.5바이트 (12bpp)
    - 화질(윤곽선 해상도)은 유지하면서 원본 데이터 용량을 RGB 대비 정확히 절반으로 줄임.

### 3. _888의 의미 (Bit Depth)
- Y 채널: 8-bit (0~255)
- U 채널: 8-bit (0~255)
- V 채널: 8-bit (0~255)
- 각 채널이 8비트 정밀도를 가진다는 것을 의미함.

### 4. 안드로이드 `YUV_420_888`만의 독특한 메모리 구조 (Plane & Stride)
개발자 입장에서 이 포맷의 가장 큰 특징은 **"메모리 레이아웃이 고정되어 있지 않은 가상(추상) 포맷"**

기기 제조사(퀄컴, 삼성 엑시노스, 미디어텍 등)의 카메라 HAL에 따라 메모리에 저장하는 방식이 다름

1. Planar 방식 (I420 등): 메모리에 `[YYYY...][UUUU...][VVVV...]` 순으로 각각 분리 저장
2. Semi-Planar 방식 (NV12 또는 NV21): Y는 모아두고, UV는 `[YYYY...][UVUV...]` 또는 `[YYYY...][VUVU...]` 형태로 인터리빙(Interleaving) 저장

안드로이드의 `Image` 객체는 이를 통일된 방식으로 읽을 수 있도록 **3개의 Plane(평면)**으로 나누어 제공함

```c++
// C++ / NDK 단에서 접근할 때의 개념
ImageReader -> Image
  Plane[0] : Y 버퍼 포인터 (pixelStride = 1, rowStride >= Width)
  Plane[1] : U 버퍼 포인터 (pixelStride, rowStride)
  Plane[2] : V 버퍼 포인터 (pixelStride, rowStride)
```

- `pixelStrde` (픽셀 보폭):
    - Y 평면은 항상 `1` (다음 픽셀이 바로 옆 바이트)
    - U/V 평면의 `pixelStride`가 `1`이면 Planar(I420), `2`이면 Semi-Planar(NV12/NV21) 형태
- `rowStride` (줄 보폭 / 패딩):
    - GPU나 하드웨어 가속을 위해 메모리를 16바이트, 64바이트 단위로 정렬(Alignment)하면서 영상 가로폭(Width) 뒤쪽에 빈 더미 데이터(Padding)가 붙는 경우가 많음
    - C++에서 1차원 포인터로 복사할 때 `Width` 단위로 그냥 읽으면 화면이 대각선으로 깨지며 밀리는 현상이 발생하므로, 반드시 `rowStride`를 고려해 행 단위로 읽어야 함

### 유속 분석 결과가 다른 이유?
1. 인코더 왜곡이 제로:
    - 카메라 센서가 빛을 받아 ISP(Image Signal Processor)에서 노이즈 제거, 디모자이크, 화이트 밸런스만 거치고 나온 순수한 프레임별 화소값
    - H.264처럼 DCT 블록화, 양자화(미세 무늬 손실), 이전 프레임을 재활용하는 움직임 예측(Motion Estimation) 등의 손실 압축 알고리즘이 개입하지 않음
2. 시간축 독립성(Frame-to-Frame Indeoendence)
    - 각 프레임이 독립적으로 찍힌 물리적 수면 상태이므로, 물결이 프레임당 몇 픽셀 이동했는지 시간-공간 축에서 직선 궤적을 나타냄


## H.264란? 
H.264(공식명칭: MPEG-4 Part 10 AVC / Advanced Video Coding)는 전 세계에서 가장 널리 쓰이는 **고효율 비디오 압축 표준(코덱)**임.

2003년 ITU-T(통신 표준화 기구)와 ISO/IEC(국제 표준화 기구)가 공동 개발했으며, 이전 세대인 MPEG-2나 MPEG-4 Part 2(DivX 등)에 비해 동일한 화질을 절반 이하의 비트레이트(용량)로 전송, 저장할 수 있도록 설계되었습니다.

H.264의 핵심 철학은 **"인간의 눈이 눈치채지 못하는 정보(중복 정보)를 최대한 깎아내어 용량을 줄인다"**

### 1. H.265가 영상을 압축하는 3가지 중복성 제거 원리
동영상을 픽셀 그대로 저장하면 수십~수백 MB의 용량이 필요하기 때문에, H.264는 세 가지 영역의 **중복성(Redundancy)**을 제거함
1. 시간적 중복성: 1초에 30프레임이 지나갈 때, 프레임 사이에는 변하지 않는 배경이 대부분임. 변하지 않은 부분은 다시 저장하지 않고 '이전 프레임의 위치'만 참조함.
2. 공간적 중복성: 하늘, 벽면처럼 한 프레임 안에서도 인접한 픽셀끼리는 색과 밝기가 비슷함. 
3. 인간 시각적 중복성(Psycho-visual Redundancy): 인간의 눈은 밝기 변화에는 민감하지만 미세한 고주파 무늬나 색상 차이에는 둔감함. 이 눈치채기 힘든 미세 신호를 버림

### 2. H.264의 핵심 기술 구조 (파이프라인)
H.264는 기본적으로 영상을 16 x 16 크기의 매크로블록(Macroblock) 단위로 쪼개어 아래의 4단계를 거쳐 인코딩함.
```
[입력 프레임]
     │
     ▼
 1. 예측 (Intra / Inter Prediction) ──> 실제 픽셀값 대신 '예측 오차(Residual)'만 추출
     │
     ▼
 2. 정수 DCT 변환 (Integer Transform) & 양자화 (Quantization) ──> 주파수 변환 후 미세 신호 버림 (손실 압축)
     │
     ▼
 3. 인루프 디블록킹 필터 (In-loop Deblocking Filter) ──> 블록 경계면을 매끄럽게 보정
     │
     ▼
 4. 엔트로피 코딩 (CAVLC / CABAC) ──> 비트 단위 무손실 압축
     │
     ▼
[H.264 비트스트림 출력]
```

(1) 프레임 타입과 예측(Prediction)
H.265는 프레임을 세 종류로 나누어 압축 효율을 극대화함.
- I-프레임 (Intra Frame, 키프레임):
    - 다른 프레임을 전혀 참조하지 않고 단독으로 압축되는 온전한 사진
    - 프레임 내부의 인접 픽셀 방향성을 보고 예측하는 Intra Prediction(16 x 16 또는 4 x 4 단위)을 사용함
- P-프레임 (Predicted Frame):
    - 이전 I 또는 P 프레임을 참조하여, 물체가 어디로 이동했는지를 나타내는 **움직임 벡터(Motion Vector, MV)**와 **오차(Residual)**만 저장함.
    - 최대 4 x 4 블록까지 가변 분할(Variable Block-size)을 지원하며, 픽셀의 1/4 단위(Quarter-pixel)까지 미세하게 움직임을 추적함
- B-프레임 (Bi-directional Frame):
    - 이전 프레임과 미래의 프레임을 양방향으로 동시에 참조하여 압축률을 높임. (실시간 처리 시 지연시간이 발생하므로 모바일 실시간 스트리밍에선 종종 끔)

(2) 정수 DCT 변환과 양자화
- 예측하고 남은 오차(Residual) 데이터에 4 x 4 또는 8 x 8 정수 DCT를 적용함
- 공간 영역의 픽셀 차이값을 주파수 영역으로 분해함.
- 양자화(Quantization, QP 파라미터): 나누기 연산을 통해 고주파 계수들을 대부분 0으로 만듦. H.264 손실의 대부분은 이 단계에서 발생

(3) 인루프 디블록킹 필터(In-loop Deblocking Filter)
- 블록 단위로 쪼개어 압축하다 보면 블록과 블록 사이의 경계선이 깍두기처럼 보이는 **블록화 현상(Block artifact)**이 생김
- H.264는 디코더와 인코더 내부 루프 안에 적응형 필터를 두어, 블록 경계선만 부드럽게 뭉개줌

(4) 엔트로피 코딩 (CAVLC / CABAC)
- 양자화된 데이터를 최종적으로 컴퓨터가 저장할 수 있도록 비트스트림으로 만듦
- 데이터의 출현 빈도에 따라 자주 나오는 패턴에는 짧은 비트를, 드물게 나오는 패턴에는 긴 비트를 할당하는 무손실 압축(허프만 코딩의 진화형)

### 1. DCT 양자화
H.264는 영상을 4 x 4 또는 8 x 8 블록으로 나누어 정수 DCT(Discrete Cosine Transform)를 수행한 뒤 고주파 성분을 강하게 양자화(버림 처리)함.
- 결과적 왜곡:
    - 물 표면의 빠른 유동 신호(미세 텍스처)는 대부분 공간 고주파에 해당하므로 양자화 과정에서 뭉개져 사라짐
    - 반면, 하천 바닥의 정지된 돌, 수면의 큰 명암 변화, 하늘/주변부의 완만한 반사광 등은 공간 저주파(DC 성분 근처)에 해당하여 H.264 압축 후에도 남는 경우가 많음
    - 결과적으로 2D FFT 스펙트럼에서 유속 0 쪽의 에너지가 보존, 증폭되는 반면, 실제 유속을 나타내는 경사 에너지는 감쇄되어 전체 피크 에너지가 낮은 속도쪽으로 쏠림(Bias)

### 2. 블록 기반 움직임 추정(Motion Estimation)의 'Zero-Vector' 편향

H.264의 하드웨어 인코더(MediaCodec)는 주로 실시간 비트레이트 절감을 목표로 동작하며, 강체(Rigid body)의 병진 운동을 전제로 최적화되어 있음

- 유체의 비강체(Non-rigid) 변형: 유체 표면은 프레임마다 계속 변형되고 흩어짐. H.264 인코더의 블록 매칭 알고리즘은 변형되는 유체 표면에서 정확한 움직임 벡터를 찾지 못할 수 있음
- Rate-Distortion 최적화 문제: 하드웨어 인코더는 적절한 매칭을 찾지 못하면 비트레이트를 아끼기 위해 **움직임 벡터를 (0,0)으로 설정(Zero-motion bias)**하고 잔차 데이터를 강하게 압축

### 3. 4x4/8x8 그리드 격자에 의한 계단 현상과 축 편향 누설
- H.264 DCT 블록: 영상이 4x4 또는 8x8 단위로 양자화되기 때문에, 픽셀 단위로 연속 이동해야 할 텍스처가 블록 단위 경계에 갇히게 됨
- STI 상의 대각선 궤적이 매끄러운 선이 아니라 격자형 '계단(StairCase)' 형태로 왜곡됨
- 계단파(Step function) 형태의 신호는 2D FFT 변환 시 대각 선 주파수 성분 외 수평축 및 수직축 방향으로 강력한 스펙트럼 누설(Spectral Leakage)을 발생시킴
