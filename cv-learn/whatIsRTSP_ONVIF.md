# RTSP 와 ONVIF
> 영상 보안 시스템에서 핵심적인 통신 규격으로, 
- ONVIF: 카메라와 녹화기가 서로 대화하는 '공통 언어 및 통합 리모컨' (기기 검색, PTZ제어, 알람, 설정 변경 등)
- RTSP: 리모컨으로 재생 버튼을 눌렀을 때 '실제 영상을 실시간으로 전송해 주는 파이프라인'

## RTSP (Real-Time Streaming Protocol)
### 1. 개념
- 실시간 스트리밍 프로토콜로, 네트워크를 통해 오디오 및 비디오 데이터를 실시간으로 제어하고 전송하기 위해 설계된 네트워크 프로토콜
- 비디오 플레이어의 재생(Play), 일시정지(Pause), 중지(Teardown) 같은 미디어 재생 제어 역할을 담당
### 2. 동작 방식
- 포트 번호: 기본적으로 554번 포트 사용
- 데이터 전송과의 관계: RTSP는 제어 신호만 주고 받으며, 실제 대용량 영상, 음성 데이터는 **RTP(Real-time Transport Protocol)**를 통해 전송되고, 전송 품질 관리는 RTCP가 담당함. (보통 RTSP 설정 시 이들이 묶여서 작동함)
- URL 주소 형태: 보통 다음과 같은 고유 주소를 통해 스트림을 직접 호출함
```
rtsp://[아이디]:[비밀번호]@[카메라IP]:554/[제조사별 고유경로]
(예: rtsp://admin:1234@192.168.1.50:554/stream1)
```
### 3. 장점 및 한계
- 장점: 제조사에 구애받지 않고 VLC 플레이어, 웹 브라우저, 스마트폰 앱, 홈 어시스턴트(Home Assistant) 등 영상재생기만 있으면 영상 스트림을 즉시 화면에 띄울 수 있음
- 한계: 오직 영상/소리 전송에만 특화되어 있음. 카메라의 각도를 돌리거나(PTZ), 움직임 감지(Motion Detection) 알림을 받거나, 해상도/야간 모드 같은 기기 설정을 변경할 수는 없음

## ONVIF(Open Network Video Interface Forum)
### 1. 개념
- 특정 단일 프로토콜이 아니라, 제조사가 서로 다른 IP 기반 보안 기기(카메라, NVR, 소프트웨어 등) 간의 **상호 호환성을 위해 만든 국제 표준 인터페이스 규격(표준 프레임워크)**
- 2008년 Axis, Bosch, Sony가 공동 설립했으며, 현재 전 세계 대부분의 CCTV 제조사(한화비전, 다후아, 하이크비전 등)가 이 표준을 준수함

### 2. 주요 기능
> 웹 서비스 기반(HTTP, XML, SOAP 등)으로 통신하며, 다음과 같은 광범위한 기능을 표준화함.

1. **장치 자동 검색(Device Discovery)**: NVR이나 프로그램에서 네트워크에 연결된 카메라를 자동으로 검색하여 찾아냄
2. **기기 및 영상 설정**: 해상도, 프레임 레이트, IP 주소 변경 등
3. **PTZ 제어**: 팬(좌우), 틸트(상하), 줌(확대/축소) 동작
4. **이벤트 및 알람 연동**: 모션 감지, 오디오 감지, 탬퍼링(카메라 가림) 이벤트 수신
5. **영상 스트리밍 호출**: 영상을 불러올 때 내부적으로 RTSP를 호출하여 연결

### 3. 프로파일(Profile) 개념
> ONVIF는 기능별로 '프로파일'을 나누어 지원함

- **Profile S**: 기본 비디오 스트리밍 및 PTZ 제어(가장 널리 쓰임)
- **Profile T**: 고효율 비디오(H.265) 스트리밍 및 고급 모션 이벤트 지원
- **Profile G**: 카메라 내부 SD카드 녹화 및 저장된 영상 검색/재생
- **Profile M**: AI 메타데이터(사람/차량 인식, 얼굴 감지 등) 전송

### RTSP vs ONVIF 핵심 비교
|구분|RTSP|ONVIF|
|-|-|-|
|성격|단일 전송/스트리밍 제어 프로토콜|기기 간 상호 운용성을 위한 표준 인터페이스(규격)|
|주요 역할|실시간 영상/음성 스트림 가져오기|기기 검색, 영상 제어, PTZ 조작, 알람 수신 등 종합 제어|
|기기 검색(Scan)|불가능 (IP와 URL 경로를 직접 입력해야 함)|가능 (동일 네트워크 내 자동 탐색)|
|PTZ/알람 제어|불가능|가능|
|사용 포트|주로 554 포트|제조사에 따라 다름 (주로 80, 8000, 8080 등 웹 포트)|
|포함 관계| ONVIF가 영상을 가져올 때 RTSP를 내부적으로 사용함|

---

> 개발자 관점에서 RTSP와 ONVIF를 다룰 때 설계, 구현에 반영해야 할 핵심 사항

### 1. 전송 방식 설정: 반드시 RTSP over TCP(Interleaved) 사용
- 문제점: 야외 하천 카메라는 LTE/무선 브릿지로 연결되는 경우가 많아 패킷 손실이 잦음. 기본값인 UDP인지 확인하여, 프레임 손실로 인해 화면 깨짐(Macroblocking), 회색 화면, 디코딩 오류가 발생하지 않도록 해야함.
- 해결책: 클라이언트 파이프라인에서 반드시 **TCP 옵션**을 강제해야 함
    - FFmpeg / OpenCV: `rtsp_transport=tcp` 설정
    - GStreamer: `rtspsrc protocols=tcp` 설정

### 2. AI 연산용과 관제용 스트림 분리 (Multi-Stream)
- 하천 수위 측정, 유속 분석, 침수 감지 등 AI 추론에 4K/FHD 고화질 프레임(30fps)을 그대로 넣으면 GPU/CPU 부하가 급증함
- 카메라의 멀티스트림 활용:
    - Sub-Stream (640x360, 5~10fps): AI 분석 엔진(수위 변화 감지, 위험구역 보행자 감지 등)에 주입
    - Main-Stream(FHD/4K, 30fps): 이벤트 발생 시 녹화본 저장, 또는 수요처 고화질 관제용으로 파이프라인 바이패스

### 3. 버퍼링 제어 및 지연(Lagency) 누적 방지
- AI 모델 추론 속도가 영상 프레임 레이트보다 느려지면 RTSP 클라이언트 내부 큐에 프레임이 쌓이면서 **지연 시간이 점점 늘어나는 문제(Latency Accumulation)**가 발생함
- 해결책: 
    - 파이프라인에서 버퍼 크기를 0으로 최소화(`buffer-size=0` or `fflags=nobuffer`)
    - 스트림 수신 스레드와 AI 추론 스레드를 분리하고, AI 스레드는 항상 최신 프레임 1장만 읽고 이전 프레임은 버리는(Drop) 링 버퍼(Ring Buffer) 구조를 적용해야 함

### 4. 코덱(Codec) 선택: H.264 vs H.265 (HEVC)
- H.265: 대역폭을 30~50% 절감하므로 외곽 하천의 무선 통신비 절감에 매우 유리함
- 주의사항: 서버/에지 디바이스에서 H.265 디코딩 시 하드웨어 가속(NVIDIA NVDEC, Intel QSV 등) 설정이 필수적이며, CPU 소프트웨어 디코딩만 쓸 경우 H.264보다 자원 소모가 급격히 커짐
